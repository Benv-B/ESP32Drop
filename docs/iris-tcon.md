## 不接屏幕的接收测速

`tools/build-receive-benchmark.ps1` 构建独立的 `xiao-c5-rx-bench-7`，输出到 `.build-rx-bench-c5-ch149/`，不覆盖显示版构建目录。它仍使用 CN / 149、相同 AWDL/TLS/解压/流队列和 4 MiB 归档上限，但不初始化 NFC、电源锁存、SPI 或显示驱动，仅 USB 给主板供电即可。

手机中名称为 **Photo Frame RX Test**。每次只发一张 JPEG；完整归档长度、CRC、cpio 和单 JPEG 校验通过后才 ACK COMMIT。成功只表示数据已在 RAM 中通过接收校验，照片不会保存、解码或显示，不代表 JPEG 像素可解码。USB 输出 JSON 状态和日志，不转发照片数据；`STATUS` 可请求状态。第 4 版在 PSRAM 中保留最近 128 条带时间戳的连接/HTTP 事件，空闲时发送 `TRACE` 可读出，未连接串口时仍记录，重启后清空；它不包含完整无线抓包，也不能找回升级前丢失的日志。记录内存分配失败只影响历史查询，不阻止接收服务；上传中拒绝历史输出，避免诊断占用接收循环。比较同一照片的 `rx_elapsed_ms`、`consumer_us`、`inflate_us` 及 `network` 计数增量。此模式没有自动关机，恢复正式相框须重新烧录显示版。

当前板上版本为第 7 版，已完成一次手机与接收端均确认成功的投送，继续保留运行。构建参数为 `-TcpRxWindow 16384 -NetifTxQueue 32`，MTU 1280、RX 环可用 31 格；实际构建目录为 `.build-rx-bench-c5-ch149-wnd16384-txq32/`。以下第 1–6 版及恢复操作均为历史测试记录；最新结果见 `logs/rx-bench-7-validation-20261022.json`。

第 5 版修复了三处可通过主机测试复现的问题：已进入发送队列的组播完成回调原先提前返回，没有释放唯一在飞槽位，现成功/失败均先按完整序号确认归属并释放；Discover 已立即回复后，将请求体逐次读取等待从 400 ms 放宽到 3000 ms，容纳约 1.049 秒的 AWDL 周期和重传，正常及时到达的请求体不会多等；固定 Content-Length 丢弃路径原先在没有读到数据、或恰好在 512 字节边界停止时可能误判完成，现必须读满声明长度。这些问题的旧代码测试失败、修复后通过，但没有足够的旧现场日志证明它们就是此前每次拒绝或超时的原因。

本轮验证：HTTP 39 项、serve 31 项、实际发送回调/在飞门控函数在两种 MTU 下共 22 项检查、TCP MSS 跟踪解析，以及 `tools/test-iris.ps1` 的 11 组主机测试通过；固定 C5 SDK 下两种 MTU 构建及 lwIP 链接来源检查通过。发送回调测试为 `tools/test-netif-tx.py`，只替换 SDK/队列边界，提取实际实现进行编译。测试不能替代长时间多次实板投送。

测速构建新增 `-NetifMtu 1460`，默认仍为 1280；该实验只允许纯接收模式，目录增加 `-mtu1460` 后缀。1460 字节 IPv6 包加 40 字节 AWDL 帧头正好是当前原始发送上限 1500，编译断言防止越界。状态输出实际 `netif_mtu`/`netif_mtu_error`，TCP SYN 跟踪输出实际 MSS；已观察到 MSS 从 1220 变为 1400。保持窗口 16384、邮箱 16、队列 32、在飞上限 1 和原 PHY 配置不变。新增 `jpeg_crc32` 与 `jpeg_bytes` 用于核对同图，避免把 AirDrop 外层压缩大小差异误作照片差异。比较还须同时检查 `ch_mask`，不能只凭文件大小及总时长归因于 MTU。

第 6 版继续优化 C5 的接收突发处理：RX 环从 16 个槽位（可用 15）增至 32（可用 31），增加约 26 KB PSRAM，S3 的环大小保持原值。C5 工作任务由每毫秒轮询改为入队后通过静态二值信号量唤醒；先发布完整帧再唤醒，空检查和等待之间到来的唤醒不会丢失，多个唤醒可合并，环本身仍决定待处理数据。停止时主动唤醒，并允许在两帧之间停止，避免持续流量拖住退出。信号量有静态生命周期，不持有可能被删除的任务句柄，不在 Wi-Fi 回调中等待或分配内存。Wi-Fi 回调应保持轻量，依据固定版本 [ESP-IDF 5.5.4 Wi-Fi 指南](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c5/api-guides/wifi.html#wi-fi-sniffer-mode)。

## 硬件连接与上电

依据用户提供的 AW1005S102 规格 v1.0 第6、10、11、14页，以及 TCON PCBA 应用说明 v1.23 第13、19–23、26、39页。使用已配套并烧有屏参的 IRIS TCON；固件不写其 Flash、PMIC 校准或波形参数。

| RevC / XIAO ESP32-C5 | 信号 | TCON 39针接口 J3 |
|---|---|---|
| GPIO8 / D8 | SPI CLK | 34 |
| GPIO10 / D10 | SPI MOSI | 35 |
| GPIO9 / D9 | SPI MISO | 36 |
| GPIO0 / D1 | CS，低有效 | 37 |
| GPIO12 / D7 | INT_DF，高有效 | 24 |
| GPIO7 / D3 | BUS_EN，隔离开关使能 | 载板 U5/Q7，不是额外 FPC 信号 |
| GPIO1 / D0 | PWR_OFF，清除电源锁存 | 载板电源控制 |
| GPIO23/24 | NFC SDA/SCL | 载板 NTAG I²C |
| GPIO5 / 底部焊盘16 | EN_LATCH 分压 ADC | 载板 R28/R29 |
| 5V_SYS | 5.0–5.5 V | 1–6，全部连接 |
| GND | 公共地 | 7/10/13/16/19/22/25 |

排线必须断电插拔，逐针确认两端映射及接触面，不能仅凭连接器外观判断方向。所有 NC 留空，31脚 AGINGEN 保持低。SPI 为 3.3 V 逻辑。供电边沿要求 0.5–10 ms，断电到重上电至少 50 ms。

先用限流电源验证载板供电与带载能力，再进行第一次刷新。手册给出最高 3 A 浪涌，RevC 三节 AA 升压电路尚未做屏幕带载验收；仅看空载约5.3 V 不足以证明能刷屏。测量点应在 TCON 供电端，刷新时保持 5.0–5.5 V。

首次检查可先不接屏：万用表黑笔插 COM、红笔插 VΩ，设直流电压档；黑笔接 J1 的 BAT−，红笔测 C7 的1脚（5V_SYS）或 D1 的阳极。C7 的2脚是 GND，不能把电流档直接跨接电源。按 SW1 后，5V_SYS应约5.3 V且在5.0–5.5 V范围内。先断电用通断档确认测量点，再通电测压，避免在0.3 mm的FPC脚间滑动表笔。空载合格后完全断电再插好排线，重新上电测TCON端供电。电压异常、反复重启或器件明显发热时停止后续刷新。

当前实板为 XIAO ESP32-C5 V1.1，USB 与 J1 同时接入时 **JP1 可以保持插上**：载板 D1 阻止 USB 回灌5V_SYS，XIAO 的 U4 TPS22916CN 提供USB路径的反向电流阻断。依据 [Seeed V1.1原理图第4页](https://files.seeedstudio.com/wiki/XIAO_ESP32C5/res/Seeed_Studio_XIAO_ESP32C5.pdf) 和 [TI TPS22916数据手册§8.3.3](https://www.ti.com/lit/ds/symlink/tps22916.pdf)，此结论更正早期载板说明中的“USB调试必须拔JP1”。JP1拔掉也可用于USB独立供XIAO的调试；脱离USB独立运行需插上。跳帽及排线在全部断电后操作。

TCON仍需J1的电池/外接电源，并按SW1或由NFC启动锁存；USB本身不会通过D1给TCON供电。仅USB给XIAO供电时，本版在EN_LATCH分压不足时保持BUS_EN=0，不启动AirDrop。ADC只判断锁存大致有效，**不是5V_SYS的PG或欠压保护**；100 ms稳定检查不能代替实际供电测量。若上电初始化失败，检查接线、供电后重新启动固件。

## 使用与格式

1. 先刷色条版本并冷启动。应看到从左到右白、青、黄、绿、品红、蓝、红、黑八条，日志出现 `M1 finished`。检查红蓝没有交换，整屏没有错行。这只验证 TCON，不验证无线和 JPEG 解码。
2. 再刷正常版。NFC 或 SW1 上电，iPhone 打开 Wi-Fi/蓝牙，在照片分享中选择 AirDrop → **Photo Frame**。
3. 每次发送一张静态 **baseline RGB/灰度 JPEG**，建议首次用小于1 MiB的图片。总解包量（JPEG和元数据）不能超过4,194,304字节，图像不超过36 MP、单边不超过16384。4 MiB不是4 MB。
4. 首版不解码 HEIC、PNG、渐进 JPEG、CMYK JPEG、视频。必要时在 iPhone 分享选项选择兼容表示或先转为 JPEG；具体发送结果取决于 iOS，固件仍检查实际文件头。关闭实况，避免附带 MOV。固件清掉 AirDrop 的 Live Photo 能力位，但不保证所有 iOS 都自动转换。
5. JPEG 先按 EXIF 1–8方向修正，默认 `AUTO` 按修正后的宽高选择横向1024×768或竖向768×1024画布，再以 `COVER` 等比例放大、居中裁剪铺满，不加白边、不拉伸。竖图以90°映射到TCON原生1024×768；横图和方图以0°映射。AUTO不检测屏幕安装方向，需要随照片横竖转动实屏观看；永久竖装应选固定90°。处理后的BGR888仍按TCON原生行序发送。
6. 仅当归档/图像校验通过且TCON已确认完整显示覆盖，才允许发送端收到成功响应：无预览走M1，有预览则M3补完最后的未显示条带。成功后留30秒继续发图；空闲180秒关机，失败后留180秒重试。接收、解码、刷新和最后 TLS 回复期间不自动关机。切断电源前进入 TCON 睡眠，断开 BUS_EN，并要求 NFC 有效无场至少500 ms。

USB 逻辑关机后 MCU 仍可能有电；屏幕保留图像也不证明整板断电。电池关机电流及 NFC 再次唤醒需拔 USB 单独验收。

| 命令 | 行为 |
|---|---|

## 实现与成功条件

- 接收：复用 C5 DvZip 分块 DATA/COMMIT 通道，PSRAM 中分配4 MiB包缓冲；检查分块偏移、包长度、CRC32、cpio完整性和单张 JPEG 约束。AppleDouble 元数据可忽略，其他文件类型/多图不偷偷丢弃后报成功。
- 解码：使用固定 C5 SDK 的 ROM TJpgDec，读取块状 RGB888，通过 EXIF/缩放映射写入2,359,296字节 BGR888 缓冲，避免分配手机全分辨率的 RGB 图。约6.25 MiB用于包和帧，另外预留 DvZip、TLS 和解码工作空间。解码的主动处理预算90秒，网络等待和预览刷新时间另计；流式输入空闲限30秒、会话限360秒，最终归档确认等待限60秒。解码失败不执行最终刷新，已完成的临时M3可能保留。[Espressif ROM TJpgDec说明](https://github.com/espressif/idf-extra-components/blob/master/esp_jpeg/README.md)。
- 初始化：每次等DF最多20秒；暖重启无启动中断时尝试 `05 01` 软件复位；DF高后再等300 ms；`57`读取一个dummy字节后的4字节INTS，要求启动成功且无错误、DF清零；`06 01`唤醒后等5 ms并回读；`08 02`选SPI；`07 01`选M1。20秒启动窗口是有界的软件选择，手册p39的至少15秒建议针对刷新完成，不是启动时间规范。
- 刷新：先清掉旧完成事件并排查错误；`09`开始；768次独立 `0C + 3072字节BGR`；`0D`结束；等待至多20秒（手册10英寸建议至少15秒）。只有 `INTS[2] bit1` 且其他错误位均为0，才视为本帧成功。不能把DF任意高电平或发送完像素当作成功。
- 错误：识别 UVLO、热关断、DRAM parity、启动/命令失败和 PMIC/EEPROM/温度传感器 NACK。超时/异常尝试手册的软件复位并隔离总线，保留错误状态，不自动重复未知结果的波形。下一次新投送可重新初始化。COMMIT失败走HTTP非成功响应，`upload_ok`不增加。

关键文件：`tcon_app.cpp`（接收消费）、`iris_archive.h`（包校验）、`iris_stream_worker.cpp`（并发解码与M3预览）、`iris_image.cpp`/`iris_image_layout.h`（解码布局）、`iris_image_color.h`（ICC识别及参考空间转换）、`iris_image_tone.h`（可选提亮）、`iris_progress.cpp`（阶段指示灯）、`iris_tcon.cpp`/`iris_tcon_protocol.h`（总线和时序）、`frame_controller.cpp`（NFC与关机）。均在 `ESP32Drop/examples/SerialPhotoBridge/`。

可选串口日志为115200、普通文本/JSON，已不兼容旧网页的二进制 USB 协议。`STATUS`输出状态；`FRAME HOLD`暂停自动关机，`FRAME AUTO`恢复，`FRAME OFF`请求安全关机，`FRAME WAKE`用于USB保持供电时重启。状态中的 `displayed`、`ints`、`error`和 `upload_ok` 用于区分传输、解码和刷新故障。日志不应当作电压测量证据。

色条版另有 `TCON PROBE`：仅在TCON未初始化且锁存有效时，临时接通总线，以2 MHz及探索性100 kHz读取DC、PM、SYSS、PARAVER，最后读INTS；另在2 MHz做MISO弱下拉、弱上拉对照，恢复输入偏置后断开总线。它不发送复位、显示开始、像素、Flash或PMIC写命令；INTS读取会清除待处理中断。返回全0/全255不能作为通信成功。初始化已成功时拒绝此诊断，以免消耗显示完成事件。

`TCON BUS`用于隔离总线自检：CS全程保持高，BUS_EN=0时比较MISO下拉、上拉、无偏置的GPIO电平与SPI接收值，并输出GPIO配置和SPI输入映射。仅当锁存连续100 ms有效时，才接通BUS_EN重复比较；锁存无效则跳过接通阶段，因此USB单独供电也能检查MCU侧。发送空时钟时不选中TCON，不发送显示命令；完成或失败均恢复CS高、BUS_EN低、MISO无偏置。锁存值不是TCON电源PG，实测供电异常或排线映射未确认时，不运行接通侧测试。

`TCON WRITE TEST`是用户明确要求的单次单向色条诊断：供电锁存有效时发送唤醒、SPI/M1配置、显示开始、768行完整BGR及显示结束，再等待最多20秒读取完成状态。它跳过启动DF/INTS前提，仅用于区分写入方向与回读故障，不是正常点屏流程；不自动执行、不自动重试、不写Flash/PMIC。日志分别报告`rows_sent`、`spi_transfer_ok`和`completion_confirmed`，只有真实且无错误的M1完成状态才能增加`displayed`。正常AirDrop版不编入这些诊断命令，也不绕过启动/完成检查。
