# C5 故障记录与回归要求

适用环境：XIAO ESP32-C5，8 MB Flash / 8 MB PSRAM，`m5stack:esp32@3.3.8`，CN / 信道 149；发送端为 iPhone 15 Pro，用户报告 iOS 26.2.2。当前产品范围是静态照片。通用归档传输仍保留，不开发实况播放或视频功能。

## 已确认的问题

| 现象 | 原因与修复 | 防止回归 |
| --- | --- | --- |
| 能收到照片数据，但大量重传，速度后来约 4 KiB/s | 混杂接收能看到帧，不代表硬件已匹配并确认。设备 MAC 已一致，C5 的 AP BSSID 比较地址仍未匹配 AWDL。将硬件 AP 接口 1 的接收 BSSID 设为 `AWDL_BSSID`，保留设备独立 MAC。对照实测中目标帧全部匹配，重复风暴消失。 | 固定 SDK 的构建脚本默认启用；`-DisableAwdlBssid` 仅用于对照诊断。升级 SDK 必须重新核对私有 `ic_set_bssid` ABI 并实测，不能只看编译通过。 |
| Photo Bridge 时有时无 | C5 安静发现阶段可能主要收到 MIF；只用 PSF 会缺少时钟样本。另一个问题是没有 PLL 样本却把信道序列视为已有时间基准。C5 改为用外部 PSF/MIF 经 gauge 校验后校时，跳过自身帧，并要求 `pll_n > 0` 才发布有效发送窗口。 | 保留 gauge 录制轨迹回放；实板同时看 `pll_n`、`gauge_health`、窗口掩码和实际发射结果。主机测试不能替代 iPhone 冷启动发现测试。 |
| `/Ask` 后很快报失败 | 接受响应先于完整请求正文，关闭或复用连接时可能截断正文、破坏下一条请求边界。C5 先按 HTTP framing 读完整正文，再接受；支持同连接或新连接上传。 | `serve_test.c` 覆盖延迟正文、分块正文、流水线 Upload、截断 Ask，以及让出新连接。 |
| 一次成功后，下张静态图在约 0.9 MB 失败，返回 502 | HWCDC 的 SOF 连接标志会短暂变成 false。旧代码提前放弃当前帧，随后新帧头插入未完成载荷，最终没有收到保存确认。现在保留原偏移等待恢复；写入后按实际接受字节计数，3 秒无进展才失败。 | `bridge_write_test.cpp` 直接测试固件使用的写入函数，模拟连接抖动、短写、FIFO 满、连续帧和时钟回绕；主机还检查 CRC 和确认。 |
| 较大归档传很久后返回 413 | 旧路径把整个解包归档放入 PSRAM，上限 6 MiB。C5 改用 256 KiB 记录缓冲和 8 KiB 消费块，总归档上限 128 MiB。 | `dvzip_test.c`、`cpio_test.c`、`host/test_stream.py` 覆盖结束标记、边界、CRC、截断和大归档。上限表示可流过的数据量，不表示板子能存下整个文件。 |
| TLS/任务初始化分配失败 | C5 内部 RAM 比 S3 紧张；仅看总空闲内存会漏掉连续块不足。C5 将无线队列载荷放到 PSRAM，控制对象留在内部 RAM，任务使用核心 0。 | 编译 C5 和 S3；实板检查 `internal_free`、`internal_largest` 和接收任务栈余量，接收时也采样。 |
| 默认地区下信道 149 启动失败 | `01` 世界默认配置被驱动拒绝。使用实际地区 `CN`，不手动扩展合法信道掩码。 | 构建参数同时指定地区和信道，启动后核对 `radio_actual_channel` 与 `radio_country`。 |

软件去重只能减少重复帧进入 lwIP 的开销，不能修复硬件 ACK。只丢弃最近已成功提交、身份及内容一致的 Retry 帧；首次听到的 Retry 帧必须接收。`dedup_test.c` 覆盖发送者/接收者、序号/分片、QoS TID、内容变化、超时和时钟回绕。

`ic_set_bssid` 是私有接口。当前结论来自固定 SDK 的调用点/反汇编核对、硬件匹配计数和对照传输；没有单独抓取空口 ACK 来证明每一帧都获得确认。该实现仍属于实验适配。

## 修改后怎样验收

1. 运行 `tools/test-bridge.ps1`：无线帧、窗口、HTTP、归档、去重、USB 写入故障模拟及 Python 查看器测试。GitHub Actions 另跑完整核心套件，新增加的去重/USB 测试也进入其中。
2. 分别编译 C5（CN/149，BSSID 默认开启）和 S3，防止芯片专用代码泄漏。不得随手升级 SDK。
3. 修改无线代码后，重启板子，打开/关闭隔空投送选择页，记录发现时间；连续发送至少 5 次静态图，核对手机提示、文件、错误计数和重试。该项是后续验收要求，目前只有上述两次连续成功记录。
4. 测吞吐用同一文件、相同距离/方向/环境，并分别记录上传字节、上传处理时间、重传和消费者等待。一次只改一个关键因素。
5. 消费者故障用 `tools/bench-stream.py` 注入丢 ACK 并检查 SHA-256；它只测本地输出链，不测无线。运行前必须停止串口查看器，确认板子空闲。

不要把“编译成功”“收到混杂帧”“已提交发射”“手机出现图标”“电脑保存完成”当作同一个成功条件。发现、无线接收、HTTP 事务、消费者交付要分别定位；接收活动或交付未完时不要刷写。

## 后续 SPI 接口约束

无线/TLS 层只产生 `AdStreamPacket`，由应用任务调用 `ad_stream_read()` 并回 `ad_stream_ack()`。库不直接访问 USB 或 SPI。DATA 的确认表示消费者接收了该块；COMMIT 的成功确认必须表示归档完整性已验证且目标已完成约定的保存，之后才回复 iPhone 上传成功。更换消费者要保留传输 ID、偏移、CRC、重复块幂等和最终确认规则。

C5 当前使用单个固定信道；没有实现跳频或多信道叠加。Wi-Fi 6 芯片标称能力不能直接代表此原始 AWDL 实现的吞吐。接收端丢弃已经收到的视频也不会减少空口数据，发送静态图应在 iPhone 分享时关闭实况。
